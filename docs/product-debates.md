# 产品设计议题

## 资产能力是否可扩展，而不是围绕样例打补丁

记录日期：2026-09-11

### 辩题

当前应用的资产展示和操作，究竟是一个用户可以自行扩展的资产台账框架，还是只围绕已有样例（例如“国泰里程”）定制出来的演示？

### 当前判断

“国泰里程”是一个资产实例名称，不应该成为功能名称或代码分支。`更新里程`可以作为所有里程类资产共有的操作；南航里程、英航 Avios 或用户自行命名的其他里程记录，都应进入同一套能力。品牌、账户或项目名称只属于数据，不属于操作模型。

因此，下面两种实现不是同一件事：

- 合理：资产类型或能力为“里程”，详情页提供“更新里程”，保存数量、估值和变动记录。
- 不合理：为“国泰里程”单独增加按钮、字段或代码路径，换一个名称就必须改应用。

### 必须回答的产品问题

用户能否在不改代码、不重新打包的情况下：

1. 新建一项自己命名的里程资产；
2. 为它填写数量、单位、估值口径和有效期等适用字段；
3. 从统一入口修改余额，并保留变动记录；
4. 修改名称或分类后仍保留同一套里程能力；
5. 删除、撤销、导出、导入并在重启后恢复；
6. 在空台账中完成以上流程，而不是依赖预置的“国泰里程”。

### 验收边界

- 功能命名按能力或资产类型，不按品牌或当前样例命名。
- 新增第二个里程品牌时，不应增加新的代码分支。
- 空台账和至少两个不同名称的里程资产必须通过同一条 UI 流程验证。
- 现有预置数据能运行，只能证明回归兼容，不能证明框架可扩展。
- 在上述验证完成前，不把应用描述为完整、通用的资产管理工具。

### 待决事项

本轮已经用真实 WebView 证明：空台账可以创建两个不同名称的里程资产，改名后仍保留里程能力，删除可撤销，重启后数据保持一致。全类型的空台账验证、字段模型版本迁移、以及所有历史“暂未开放”操作仍未完成，因此本议题继续作为产品验收边界保留。

### 本轮结构审阅与修复

- 模板和“添加资产”现在进入通用编辑器并真正创建记录。
- 所有资产详情都有统一的“编辑信息”入口；里程余额仍有专用的“更新里程”快捷操作。
- 自然语言添加复用同一个资产构造器，避免手动添加与 AI 添加产生两套数据形状。
- 资产搜索图标现在可按名称、分类和单位筛选。
- 路由会取消旧的延时跳转，避免快速连续操作时页面被过期回调重绘。
- 已完成本轮前端边界拆分：`demo/index.html`、`demo/styles.css`、`demo/domain.js`、`demo/app.js` 和 `demo/storage.js` 分工明确。仍需后续处理：SQLite state 的结构演进和金融资产模块；历史上的“转账记录”“核对会籍”等按钮属于当前非目标，不纳入本轮或后续默认范围。
